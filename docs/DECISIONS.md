### D31 讨论模式：点名 / 交给负责人（补充裁决，编号由用户指定）
- **决策：** 用户只面对两种模式：
  1. **点名：** 输入里有 @ 就是点名，被 @ 的成员直接回答，负责人不介入；@ 多个成员时，各自独立回答、并排显示。被点名的成员出故障时不自动换人，只显示一行提示，附「交给负责人」按钮。
  2. **交给负责人：** 没有 @ 时默认走这个模式。界面上不设模式切换按钮。
- **负责人内部做法**（由 Core 按任务类型自动选择，对用户不暴露成模式）：
  - 单人完成：默认做法；
  - 审查：一人做、一人挑错，负责人汇总；
  - 辩论：用于有争议的判断；
  - 并行对比：用于主观类结果，由用户挑选。
- **规则：** 选用的做法记录在默认折叠的协作卡里。用户可以用自然语言要求换做法，例如「换成辩论」。敏感任务只用单人完成。额度紧张时，多人做法自动降为单人完成，并计入后台任务的额度限制（D46）。
- **排期：** P0 做点名，以及交给负责人后的单人完成；审查、辩论、并行对比放到 P1。
- **作废：** 原文档里的「指定 / 托管 / 并行」三种模式作废，并行改为负责人的内部做法之一。
- **修订对象：** 细化 D1（D1 原有的「辩论、审查、单人完成由负责人自己选」保留，增加「并行对比」）；PRODUCT 8.2 输入框里的「[我点名 ▾]」切换按钮、8.3 输入框/并排对比/协作过程、8.4「5 种模式的弹层」、9.4「按任务选架构」与「自动接班」、16 P1/P2。
- **状态：** 有效。

#### D64 实现注 a：备份改用公钥加密（**待负责人确认**）
- **冲突：** 原备份用 restic。restic 每次备份都要在服务器 / 电脑上拿到仓库口令（`RESTIC_PASSWORD`），而 restic 只有对称加密：这个口令就是「备份口令」，放在服务器上违反 D64「主密钥不得进服务器」。
- **选项：** ① restic + 用公钥加密保存 restic 口令（口令仍要放在服务器上才能备份，冲突没解决）；② restic 换成 duplicity + GPG 公钥（能增量，但要在服务器和 Windows 上维护 GPG 钥匙圈，还要本地缓存，复杂、易错）；③ **每次备份打成一个压缩包，用 age 的 X25519 公钥加密后上传**（age：一个小程序，一行命令，格式公开、稳定）。
- **选择：③。** 服务器和电脑上只放公钥（`age1…`，不是秘密），只能加密、不能解密；私钥 = 主密钥，只在用户手里，只在恢复时临时提供。上传用 rclone（S3 兼容存储都支持）。
- **代价：** 没有 restic 的去重 / 增量，每次都是完整备份；单用户数据量小（数据库导出 + 上传文件），可以接受；保留策略（每天 7 份、每周 4 份、每月 6 份）照旧，由脚本按文件名里的时间清理。备份后的完整性检查改为「重新下载、核对 SHA-256 和 age 文件头」；能不能真正解开，由恢复演练（需要主密钥）验证。
- **「盐值和 KDF 参数」：** X25519 公钥加密没有盐值和 KDF。每份备份旁边的 `.meta.json`（明文）记录格式版本、算法、加密用的公钥、密文 SHA-256，满足「非秘密参数跟随备份」。若将来改用口令（scrypt），其盐值和工作因子同样写进 meta。
- **`.env` 随备份：** 因为备份只能用主密钥打开，`.env`（含 `LITELLM_SALT_KEY`、S3 访问密钥等）现在放进加密备份包里一起保存（`BACKUP_INCLUDE_ENV=1`，默认开）。这样用户只需离线保管主密钥这一个秘密；原来「`LITELLM_SALT_KEY` 和 `RESTIC_PASSWORD` 另行离线保存」的要求取消。

#### D64 实现注 b：主密钥在用户自己的电脑上离线生成（**待负责人确认**）
- **冲突：** D64 写「生成后用安全表单交给用户」。Hark 的安全表单只能**向用户收集**秘密，不能把秘密**发给**用户；而且如果由主程序员或服务器生成，主密钥就已经进过服务器 / 聊天环境，违反同一条的「不得进服务器、任何聊天」。
- **做法：** 主密钥由 Windows 安装程序在用户自己的电脑上**离线**生成（内置官方 age-keygen，不联网，私钥只在内存里，不写盘、不进日志）。生成后弹出一个大字号、读屏软件能读的窗口，一次性显示主密钥，带「复制」「打印」两个按钮（打印 = 纸质副本）和「已保存」按钮；用户点「已保存」之前安装不会继续（满足「点击『已保存』后才算完成」）。只把公钥写进配置。
- **这个窗口就是 D64 所说的「安全表单」的替代**，请负责人确认可以这样理解。
- **服务器用同一个主密钥（D65）：** 公钥不是秘密，用户可以把窗口里显示的公钥（`age1…` 开头）照常发给主程序员，填进服务器 `.env` 的 `BACKUP_AGE_RECIPIENT`。服务器上的备份在拿到公钥之前不会运行（脚本会明确报错），这期间服务器没有异地备份。

#### D65 实现注 a：Windows 关机前备份的限制（**待负责人确认**）

### H4 D73 的实现
- 主人令牌（只有 Shell 持有，只在用户登录后的界面操作里用）发起的新增 / 换 Key = 普通确认（记 `confirm.normal` 审计）；操作员令牌发起 = 重要确认，操作员完成不了（D62）→ 403。删除 Key 不论谁发起都是重要确认（服务器还要重新验证 Cloudflare Access）。Core 没有「查看明文」「导出」接口，`keys:read-plaintext`、`keys:export` 仍在禁止清单里。

### H5 对话链路：LobeHub → Core /v1 → LiteLLM（不是 LobeHub 直连 LiteLLM）
- **做法：** LobeHub 的 OpenAI 兼容服务商指向 Core 的 `/v1`（只露出一个模型「Aroomo」，令牌 `CORE_CHAT_TOKEN`，与主人令牌分开）。Core 只决定「交给谁」（D31）：有 @ → 被点名的成员直接回答（多人各自回答，P0 按顺序分段显示）；没有 @ → 负责人；被点名成员出错只回一行提示，不自动换人。然后把请求**原样**转给 LiteLLM（只换 `model` 为成员在 LiteLLM 里的模型名、去掉正文里的 @），流式输出原样回传，只在开头插提示、在结尾插署名（「— 名字（负责人）」）。LobeHub 的系统任务（起标题等，模型名不是 `aroomo`）直接交给负责人，不加任何东西。
- **为什么不让 LobeHub 直连 LiteLLM：** ① P0 范围写明「Core 路由（最小可用：点名 + 交给负责人后的单人完成，D31）」，直连就没有 Core 路由；② LobeHub 要在启动时写死模型列表，用户新填的 Key 不重启就看不到；③ SEQUENCES.md「发一句话」本来就是 LobeHub → Core → LiteLLM。
- **与 D70 / D76 不冲突：** Core 不碰供应商 Key、不调用供应商、不做重试 / 回退 / 负载均衡 / 计费——这些仍全在 LiteLLM（单一权威来源 D45）。Core 只是在 LiteLLM 前面选成员。
- **P0 限制：** 多人点名不是并排显示（要改 LobeHub 消息组件，薄层做不到；最小改动方案：P1 由 Shell 识别 Core 输出的分段标记，渲染成左右并排）；「交给负责人」按钮暂用文字说明代替（「去掉 @ 再发一次」）；输入框 @ 联想见 H3。
- **撤回方法：** `.env` 设 `LOBE_OPENAI_PROXY_URL=http://litellm:4000/v1`、`LOBE_OPENAI_API_KEY=<LiteLLM 虚拟 Key>`，并改 `OPENAI_MODEL_LIST`。
- 删掉某个模型的最后一个 Key 时，对应成员自动停用（可以重新启用），避免负责人指向调不通的模型。
