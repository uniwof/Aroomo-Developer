# Muse 评审 1–15（原文）

> 来源：用户 2026-10-28 补交的 Muse 原始评审，逐字收录。评审对象为当时的 v4 / v4.1 / v4.2 文档；采纳情况见 DECISIONS D39、D86 和本文末对照表。

已读完纠正后的仓库 `uniwof/Aroomo-developer` 下三份文档，按 v4.2 ＞ v4.1 ＞ v4 的优先级评审。只挑错，不附和。

### 1
- **问题：** 开发流水线被“用户人肉转发”卡死，而且负责人权限自相矛盾。
- **严重程度：** 高
- **依据：** v4.2 第 1.1 节：负责人“只读仓库（通过公开链接）；不接触任何凭据”；第 1.2 节：所有任务说明、PR 链接、回复、修改意见都要经用户转发，用户还要在 GitHub 上合并 PR。这与 v4 第 0.1 节“接手 AI 全权修改或重构整个项目”直接冲突，也与 v4 第 3 节“用户的时间最宝贵”“少打扰”冲突。用户按 v4.1 第 4 节是不写代码、不搭环境的人，却成了唯一的合并者和审查通道；她一离线、F一漏转，整条线就停摆。更糟的是，Jules 按 v4.2 第 1.1 节“只有 aroomo-app 仓库；不持有任何线上凭据”，却在 P0 被分了仓库骨架、compose 三档、安装脚本、CI、部署文档——没有主机、没有凭据，它根本验证不了自己写的部署。
- **建议的改法：** 砍掉“用户转发一切”：给负责人 GitHub 的只读 + PR 评论权限，用户只点合并；给 Jules 一个可丢弃的测试主机和测试凭据，部署类任务必须在测试主机上跑通才算完成；写明用户 48 小时未回复时的默认动作（挂起还是负责人代行），不要让“等用户”成为默认状态。

### 2
- **问题：** 免费主机和部署档位的资源账根本算不过来，完整版已经顶格。
- **严重程度：** 高
- **依据：** v4 第 7.3 节：完整版“≥8 GB（建议 12 GB）、2 核，全部模块”；第 7.5 节：Oracle Always Free 已从 4 OCPU / 24 GB 减半为 2 OCPU / 12 GB。也就是说推荐配置正好等于免费上限，没有给浏览器任务、Karakeep 抓取、Meilisearch 索引留余量。v4 第 9.7 节又要求服务器上最多同时跑 2 个浏览器任务，而 Karakeep 本身就用无头 Chrome 抓取并建索引。v4 第 7.3 节的精简版更离谱：2 GB 内存要跑 LobeHub、LiteLLM、Core、PostgreSQL 四个服务。文档第 20 节自己要求“开工前验证各档位实测内存占用”，但第 16 节路线图却把 P0 部署当成已定方案先上了。
- **建议的改法：** P0 的第一件事改成实测：逐个容器给内存预算并跑 2 并发浏览器任务，超了就砍模块，不要先定档位再测。删掉 2 GB 档位，或者改名叫“仅对话演示版”；Oracle 只当候选主机，备份必须放在会被回收的主机之外，并写明被回收后的恢复步骤。

### 3
- **问题：** 主程序员是按传闻选的，备用方案还是同一个来源，相关性失效。
- **严重程度：** 高
- **依据：** v4.2 第 1.1 节：Hark 被选为主程序员的理由是“社区评价：同场对比中逻辑、编码、浏览器任务表现最稳定；据传主模型路由到 Opus 5.5，未经官方确认”。同一节又说“不做比赛选拔：为了节省额度，按社区评价直接确定分工”。备用主程序员是“另一个 Hark 账号；其次 Jules”——换账号不换厂商、不换模型族，额度、风控、模型缺陷大概率同时出问题。这不是冗余，是把单点故障换了个名字。
- **建议的改法：** 在准备期用同一份小任务（骨架 + 一个带测试的真实模块）实测 Hark 和 Jules 各一次，以通过率和返工次数定主程序员，不要用“据传”定。备用必须跨厂商（例如 Hark 挂了由本地/另一家编码智能体接手），并写明切换触发条件是“连续两期验收不合格”还是“额度用完”，两者不要混用。

### 4
- **问题：** Telethon userbot + 网页代办自动注册/登录/拿 Key，是把封号当成正常损耗。
- **严重程度：** 高
- **依据：** v4 第 6 节：Telethon“用用户自己的 TG 账号，建议用副号”；第 9.7 节：网页代办做注册、登录、签到、拿 Key、保持登录；第 9.8 节：账号管家“自动续期”。但 Telethon 是以真实用户身份走 MTProto，滥用会被限流乃至封号，公开资料明确提醒“如果滥用，你的账号会被封”，发消息过快会触发 `FloodWaitError` 甚至永久封禁。文档对各网站的自动化注册、爬取、验证码绕过是否违反其服务条款，只字未提，只写了“白名单域名”和“信任级别”，这是把合规风险推给了执行时。
- **建议的改法：** 入职流程里加一道强制的服务条款检查：禁止自动化注册/代操作的网站直接拒绝入职，不要先注册再说。Telegram 入口先用 Bot API，userbot 只读、只用一次性副号、绝不用主号；每个自动注册的账号都要在档案里写明“封号即丢弃”，并准备好封号后的 Key 轮换流程。

### 5
- **问题：** 旧 Key 迁移方案本身就是弱加密 + 责任不清，迁完还不轮换。
- **严重程度：** 高
- **依据：** v4 第 13.2 节：旧 Key 用 `HMAC-SHA256(ACCESS_TOKEN, "agc-keystore-v1")` 派生的密钥做 AES-GCM 加密，存在 Durable Objects 里，再“在本机用 wrangler 运行一次性导出脚本，解密后直接写入 LiteLLM，不经过聊天、日志，也不落盘”。HMAC 不是密钥派生函数，没有盐、没有迭代成本，ACCESS_TOKEN 本身又是最高权限的 bearer 凭据——它一泄漏，全部旧 Key 全泄漏。谁跑这个脚本也没写清：v4.2 说负责人不接触任何凭据，v4 第 19 节又要求用户通过安全表单交 ACCESS_TOKEN，执行者到底是谁、脚本由谁审计、跑完 ACCESS_TOKEN 是否作废，全没写。迁完之后旧 DO 里的数据、旧 Key 是否继续有效，也没说。
- **建议的改法：** 改用带盐的正规 KDF（如 Argon2id/scrypt）派生迁移密钥，迁移脚本由用户在本地跑、负责人只审脚本不碰凭据；迁移完成后立即轮换全部 Key、作废旧 ACCESS_TOKEN、删除旧 DO 数据，并写明 LiteLLM 侧 Key 在数据库里是明文还是加密存储。

### 6
- **问题：** “LobeHub Fork + 以后整体迁移到别的底座”是画饼，许可证也卡住了变现路。
- **严重程度：** 高
- **依据：** v4 第 11.1 节：Shell 要改的东西包括隐藏发现页和市场、删除朗读、补齐删除/排序/置顶/批量操作、热度卡、协作卡、接管卡、账号页、收件箱——这些全是 LobeHub 核心界面的改动。v4.1 第 3 节却说自研部分要和 LobeHub 本体“解耦，通过接口交互，保证以后可以整体迁移到别的底座”。一个深度 Fork 的前端不可能靠“尽量隔离在独立目录”（v4 第 6 节）就整体迁移，换底座等于重写 Shell。许可证上，LobeHub 官方口径是：二次开发并商业化需要获取商业化授权；Karakeep 是 AGPL-3.0，修改后对外提供服务必须公开修改后的源码，v4.1 第 3 节自己也承认这一点，但 v4 第 6 节却轻描淡写说“只用后端，界面由 Aroomo 渲染，自用不受 AGPL 影响”——自用和以后多用户变现是两条路，不能用前者给后者背书。
- **建议的改法：** 现在就二选一并写进决策日志：要么彻底放弃变现、接受 Fork 锁死；要么不 Fork，Aroomo 自己做 UI、只把 LobeHub 当可替换的对话后端调用（先验证它有没有这样的 API）。在拿到 LobeHub 商业授权报价之前，删掉 v4.1 第 3 节里的变现预留和多用户 tenant_id，不要为不存在的商业模式预付架构成本。

### 7
- **问题：** “Core 是唯一大脑，各项目不直接调用”没有接口契约，事实来源会打架。
- **严重程度：** 高
- **依据：** v4 第 5.2 节：“Aroomo Core 是唯一的‘大脑服务’。各开源项目之间不直接互相调用，都经过 Core 的适配层；以后替换任何一个项目都不影响整体。”但三份文档里没有任何一张消息流时序图、没有 Core 与 LobeHub / LiteLLM / Karakeep 之间的 API 契约、事件格式、失败重试和版本规则。第 12 节的数据实体本身就重叠：成员信息同时存在 LiteLLM 模型组、LobeHub、Core 资源档案里；收藏同时存在 Karakeep 和 Core 的 Item 表里。LobeHub 自己已经有会话、任务、技能、模型路由，Core 再建一套负责人、需求真源、意见台账，两个“大脑”必然以其中一个的静默覆盖告终。
- **建议的改法：** 先定“一个实体只有一个事实来源”（例如成员归 LiteLLM、收藏归 Karakeep、需求版本归 Core），其他地方只存引用 ID；P0 交付物里必须有三条核心链路的时序图（发一句话、网页代办注册拿 Key、负责人换人），画不出来就说明架构还没想清楚，删掉“替换任何项目都不影响整体”这句话。

### 8
- **问题：** Groq 免费档被当成“运行时员工”，后台任务会先把用户自己的额度烧光。
- **严重程度：** 高
- **依据：** v4.2 第 1.1 节：Groq（免费 API）上线后做分类、抽取、语音转写、初审；v4 第 9.8 节：资源管家、挖掘员、市场研究员等后台员工全是 AI 定时任务；第 10 节 I1 额度清仓、I10 影子测试（用真实任务副本跑新成员）还要再烧一遍。Groq 免费档的主力模型是每天 1000 请求、每天 200000 token，且限额按组织算、多个 Key 共用同一池子。后台定时任务、影子副本、雷达评分、健康心跳全挤这一个池子，用户白天一用就 429。v4 第 10 节 I11 的兜底是“降级到本地模型或免 Key 公共接口”，这个公共接口是谁、会不会把用户内容发出去，文档没写；I16 的零花费保证（LiteLLM 预算设 0 + 禁用 spend）又和“自动回退到下一个成员”直接打架。
- **建议的改法：** 给后台员工单独的 token/请求预算，影子测试默认关闭、只在用户手动批准时跑；Groq 额度耗尽时明确行为是排队等待而不是静默降级到不明公共接口；删掉 I11 里“免 Key 公共接口”这个兜底，或者写清它到底是哪个服务、发什么数据。

### 9
- **问题：** 网页资源一会儿是成员、一会儿是工具，咨询包的“不含敏感信息”没有实现手段。
- **严重程度：** 高
- **依据：** v4.1 第 1.1 节：网页版 AI“身份上仍是成员”，用法上“只能担任顾问”；v4.2 第 2.2 节：生成型网页资源“属于工具，而不是成员”，并说这条“修订了 v4 里生图等模型也算成员的说法，仅适用于网页资源；通过 API 接入的生图、配音模型仍然是成员”。同一个能力，换个接入方式就换身份，路由、绩效、额度圆环、每日上限全乱套。限额本身也打架：v4.1 第 1.4 节顾问默认每天 5 次，v4.2 第 2.3 节网页工具默认每天 10 次，一个既是顾问又是工具的资源到底按哪个算？v4.1 第 1.4 节要求咨询包“总长度默认不超过 3000 字，不含任何敏感信息”，但敏感信息的识别靠 v4 第 6 节里还是“候选”、第 20 节要求“部署前核实中文识别效果”的 Presidio——等于把核心隐私防线押在一个没验证过的候选组件上。
- **建议的改法：** 按能力而不是按接入方式定身份：会推理判断的叫顾问、只出文件的叫工具，写一张统一的限额表覆盖两种接入。咨询包在发出前必须经过脱敏检查并留审计记录，Presidio 中文效果在 P2 之前实测不过就改成人工确认 + 关键词拦截，不要先上线再验证。

### 10
- **问题：** 密钥扫描、用量告警、一键紧急锁定写得很满，但没有一个执行点能同时管住所有服务。
- **严重程度：** 中
- **依据：** v4.1 第 2.6 节：X1“每次提交代码、每条外发消息都扫描 Key 和令牌，发现即拦截”（必，P1）、X2“用量突然暴涨时自动停用该 Key”（必，P2）、X3“一键紧急锁定：暂停所有后台员工、作废所有操作员令牌、冻结网页代办”（必，P3）。但执行面是 LobeHub、LiteLLM、Karakeep、MetaMCP、TG userbot、网页代办、Jules 云 VM、Hark 主机八个互不隶属的系统，文档没写扫描挂在哪一层、停用 Key 调的是哪个 API、作废令牌怎么覆盖已经发出去的会话。LiteLLM 的审计日志、SSO、JWT 鉴权本身就在企业版里，免费版拿不到现成的审计能力，v4 第 9.3 节操作员令牌“只能拿到执行状态”也挡不住“用网页代办任务参数把凭据带出去”这种间接泄露。第 9.7 节“关键步骤截图（密码框和 Key 自动打码）”同样依赖自动打码的可靠性，没写打码失败时的处理。
- **建议的改法：** 把 X1/X2/X3 降级为“检查清单 + 手动流程”先行：git 提交用 pre-receive 钩子扫、LiteLLM 侧用预算硬停、外发消息走 Core 统一出口扫；紧急锁定写成按服务逐项执行的操作手册并实测一次，不要再写“一键”。

### 11
- **问题：** 点子热度雷达的数据源假设已经过期，假热度检测没有算法。
- **严重程度：** 中
- **依据：** v4 第 6 节：RSSHub“把 X、Telegram、Reddit、Instagram 等转成 RSS，供挖掘员和点子雷达使用”；第 9.11 节：数据源包括 Reddit、X、Telegram 公开频道、V2EX、知乎等，评分维度里有“热度趋势（最近 30 天讨论量和搜索量变化率）”。但自托管 RSSHub 的 X 路由需要登录态 Cookie 或付费 X API 密钥，官方配置文档也要求为 Twitter 路由配账号、密码、auth_token 等登录信息。第 20 节自己承认“雷达各数据源在 RSSHub 中是否可用，哪些需要 Cookie”要部署前核实，却把雷达排进了 P5 的验收项。第 9.11 节的防假热度只有一句话——“按独立作者去重，并降低营销号的权重”——没有作者身份定义、没有刷屏阈值、没有聚类规则；Google Trends“没有官方免费 API”、百度指数“需要登录”，这两个趋势源一断，热度趋势这一维只能填 0 或者编分。
- **建议的改法：** P0 就逐个数据源实测“无登录能不能拿到、多久被限流”，拿不到的直接从 MVP 里删掉，不要留到 P5 再发现。假热度检测先写成可测试的规则（同一话题 24 小时内独立作者数、重复文本相似度阈值），缺失数据源的维度记为“未知”而不是 0 分。

### 12
- **问题：** 功能清单是 45 条新增 + 23 项创新，单用户自用项目没有 MVP，也没有砍功能的标准。
- **严重程度：** 中
- **依据：** v4.1 第 2 节共 45 条建议排入各期，v4 第 10 节共 23 项创新功能，v4 第 16 节 P0–P7 一路排到 WhatsApp、自举开发通道、点子验证闭环。v4.1 第 3 节还要在第一版就预留 tenant_id、多用户权限、免费版/付费版功能开关——一个明确写着“当前定位是自用”的项目，先给不存在的多用户和变现交架构税。v4 第 3 节的原则是“用最小的面积承载最多的功能”“用户只看结果”，但 P1–P2 就已经塞了健康分、自动换人、协作卡、需求真源、并排对比、虚拟 Key、零花费保证，核心对话还没被证明稳定，装饰已经先上了。
- **建议的改法：** 重新定义 MVP：对话 + LiteLLM 网关 + Core 路由 + 备份 + 收件箱，五样之外全部移到“观察”列。给每个 P4 之后的功能写一条砍掉条件（例如连续两期没人用、维护成本超过收益），每期评审先过砍掉清单再谈新增。

### 13
- **问题：** “少打扰”是个口号：接管卡、到期提醒、开发转发全在突破打扰预算。
- **严重程度：** 中
- **依据：** v4 第 9.9 节：每天即时推送不超过 3 次，“只有接管、付款、阻塞性决定可以突破预算”；但第 9.7 节：验证码、两步验证、人机验证、付款都要推接管卡，30 分钟无人处理就超时挂起——网页代办本来就是高频触发验证码的活，等于给“突破预算”开了个常用通道。再加上 v4.2 第 3.1 节入职流程的询问卡、到期前 7 天提醒、流程失败进收件箱，以及第 1.2 节开发流程里用户要转发每一条任务和回复，真实打扰量远超 3 次。第 8.3 节要求所有列表支持删除可撤销（回收站 30 天），却没写智能体删账号、取消试用、作废 Key 这类不可逆动作有没有撤销或二次确认。
- **建议的改法：** 把接管请求也计入打扰预算，超预算的接管任务自动取消而不是挂起等用户；开发类消息和产品类消息分两个通道，开发消息只进每日汇总；所有不可逆动作（删账号、取消试用、作废 Key、删项目）强制二次确认并写审计，回收站只管数据删除。

### 14
- **问题：** 备份和值班哨兵的承诺经不起“免费平台会丢东西”这一关。
- **严重程度：** 中
- **依据：** v4 第 7.6 节：每天加密备份数据库、配置、网页流程、保险箱到 WebDAV 或 S3，每月做一次恢复演练；第 7.4 节：值班哨兵“不到 256 MB 内存，能被请求唤醒的免费容器平台就能跑”。但第 7.5 节自己写了 Koyeb 免费档“不能挂持久卷，1 小时没流量就缩到零”——哨兵的暂存队列如果放在本地磁盘，缩到零就等于丢消息；如果放在别处，文档没写放在哪、丢了怎么发现。第 7.6 节也没写备份的加密密钥由谁保管、保留几份、恢复演练的 RTO 是多少；Karakeep 全文快照 + 网页代办截图（第 9.7 节保存 30 天）+ 流程录像全算进“至少 40 GB”（第 7.2 节）里，没有按数据类型分保留策略，40 GB 被截图和快照吃光只是时间问题。
- **建议的改法：** 哨兵队列必须用外部持久队列（或直接落到 Telegram/Bark 之外的持久存储并带确认回执），本地磁盘暂存视为不可靠。备份写清密钥保管人、保留份数、按数据类型分的保留期，P0 就做一次真实恢复演练并记录耗时，演练失败不许进 P1。
