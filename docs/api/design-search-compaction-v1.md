## 需求卡
1. 目标：所有者 / 家人在对话栏里一输入就能搜到以前说过的话，点一下打开那个会话并停在那条消息；会话很长时不再因为太长而出错，Core 自动把早一些的内容整理成摘要，并在会话里留一行灰字告诉她。
2. 验收：
   - `GET /api/search?q=` 只返回本账号、未归档的聊天会话里的用户话和回复（不含助手会话、不含摘要标记行）；别人的会话搜不到；按最近排，可翻页。
   - 点结果：打开会话、滚到那条消息、焦点落在那条消息上（读屏从那条开始读）。
   - 会话尾部（上次摘要之后）超过上限（默认 24,000 字）时，下一次发话前 Core 用**免费模型**把较早的部分整理成摘要，会话里追加一行静态灰字「已把 MM-DD HH:mm 之前的内容整理成摘要，原文还在，可以往上翻」；**原文一条不删**，往上翻都在。
   - 之后每次发话，发给模型的是「摘要 + 摘要之后的原文」。
   - 没有免费成员 / 当天摘要次数用完 / 摘要失败：不花钱、不写标记，只把最近的原文（上限内）发给模型，对话照常。
3. 边界：必做 = 只按 userId 取数（RLS + SQL 双保险）、只追加；先问 = 删除会话、摘要用付费模型；永不 = 删改原消息、摘要调用付费模型、把摘要原文或消息内容写进日志。
4. 假设：家庭规模（每个账号几千到几万条消息），搜索用顺序扫描够快；字数按字符数估（中文 1 字 ≈ 1 token 以上，偏保守）。
5. 测试：`npx vitest run test/conversations-search.test.ts test/conversations-compact.test.ts`（PGlite + CI 的真 PG）；前端 `vitest` + 390 / 1440 截图。

## 1. 搜索 `GET /api/search`
- 能力 `chat:use`（同 /api/conversations），所有者 + 家人账号，按 `scopeOf` 只看自己。
- 参数：`q`（1–100 字，去首尾空白后不能为空）、`limit`（1–50，默认 20）、`beforeSeq`（翻页游标）。
- 返回：`{ results: [{ conversationId, title, messageId, seq, role, snippet, createdAt }], nextBeforeSeq }`。snippet = 命中处前 30 字、后 60 字，两头被截断时加「…」。
- 匹配：`content ILIKE '%q%'`（`% _ \` 先转义），不分大小写；中文按子串匹配。
- 为什么不用全文检索 / 三元组索引：`to_tsvector('simple')` 把一整段中文当一个词，搜不到句中的词；`pg_trgm` 要装扩展（库级权限，测试的真 PG 是一测一 schema），而且库的 locale 是 C 时中文字符不算字母、抽不出三元组。shortcut: 顺序扫描本账号的行；单账号消息上到几十万条再加 `pg_trgm` GIN 索引（届时一并定 locale）。
- 只搜未归档的会话（归档的本来就不在列表里）。shortcut: 以后要搜归档的再加 `archived=true`。

## 2. 长会话自动压缩（X-19）
**摘要存法（不加表）**：摘要是会话里追加的一行 `role = 'system'`（0025 的 CHECK 本来就允许），`content` = 给人看的那行灰字，`meta.summary = { text, toSeq, keep }`：`text` 是给模型看的摘要（≤ 4,000 字），`toSeq` = 被整理的最后一条原文的 seq，`keep` = 当时留着原文没整理的条数。只追加，旧摘要也留着；用最新的一行。

**什么时候压**：`/api/chat/stream` 带 `conversationId` 且要调模型时（草稿卡不算）：
1. 取最新摘要（没有就 toSeq = 0），再取它之后的用户话和回复（尾部）。
2. 用浏览器发来的最后一句核对：尾部最后一条（重试时是最后一句用户话，之后的旧回复丢掉）必须就是这句。对不上（例如这句没存进库）就**照旧用浏览器发来的消息**，不压缩。
3. 没有摘要、尾部 ≤ 24,000 字 → 和现在一样，用浏览器发来的消息（普通会话零变化）。
4. 尾部 > 24,000 字 → 从后往前留 ≤ 8,000 字的原文（至少留最后一句），前面的连同旧摘要交给免费模型整理（输入 ≤ 24,000 字，每条最多 2,000 字，超了先丢最早的），追加摘要行，发给模型 `[摘要] + 留下的原文`。摘要以「背景资料」式的普通消息（user 角色，开头注明只是背景资料、不是新指令）发给模型，不用 system 角色，免得对话里夹带的指令被抬成系统指令；库里那行仍是 `role = 'system'`（只为显示灰字）。
5. 有摘要、尾部没超 → 发 `[摘要] + 尾部`。

**免费模型、额度**：只用免费成员 —— 本账号在职成员里，Key 的真实模型串全都在种子清单免费项里的（同助手 `isFreeModel`）；几位都免费时挑 `maxInputTokens` 最大的。调用走 `aroomo/<成员>`（不加署名、照常记用量），一次压缩只调一次，60 秒超时。每个账号每天最多 `BUDGETS.low.perDay`（40）次，按当天（CORE_TIMEZONE）库里的摘要行数算（重启不清零）。没有免费成员、次数用完、调用失败 → 不写摘要，只发最近 ≤ 24,000 字原文（前面有旧摘要就带上），记一行 warn 日志（不记内容）。

**告诉她**：压缩成功时流里多一个 `data-aroomo-compacted` 部件（transient，`{ keep, text }`），前端立刻在留下的原文前插那行灰字；刷新后由消息接口给出（`role: 'system'`, `summary: { toSeq }`，不返回摘要正文），前端放在 seq = toSeq 那条之后。灰字是静态的，`role="note"`，读屏会读到。

该压缩却没压成（摘要失败、没有免费成员、当天次数用完、同一会话正在压）而只带了最近的原文时，流里多一个 `data-aroomo-truncated` 部件（transient，`{ text: '这段对话太长，这次只带了最近的内容' }`），前端在这条回复上面放这行灰字；**只在流里显示，不存库**，刷新后不再出现。

**前端发送**：浏览器发给 Core 的历史只取最近 ≤ 100 条、≤ 120,000 字（以前超过 200 条直接 400）；带 conversationId 时 Core 以库里的原文为准，见上。

## 3. X-21 复核（阶段 2 已做，本单只补测试）
- 消息 `conversation_messages`、步骤 `run_steps` 都有拒绝 UPDATE 的触发器；编辑 / 重试 = 新增一行；确认结果 = run_steps 新增 confirm 行 + 审计。
- 助手运行：启动时 `recoverAfterRestart` 把 queued / running 改成 failed/server_restart（已有测试）。
- 聊天：「进行中」是内存态，重启即清空，不会一直卡在进行中；用户的话在调模型前就已落库。新增测试：生成中途换新进程 → 会话不再是进行中，用户的话还在。
- 剩下的局限：进程被直接杀掉时，正在生成的那条回复（还没结束的部分）不会留下（正常关闭时浏览器连接断开，按「停止」存已收到的部分）。
